1. Infrastructure as Code

Problem Statement

FlashCart’s engineers built the dev network by hand in the console: a VPC, four subnets, an internet gateway, route tables, and a NAT gateway. A week later they built production the same way, but a route table entry was missing and a security group was wider than in dev. Nobody could say exactly what was in either environment, and a new Region would take days.

The architects ask whether the environments can be described once, reviewed, and built the same way every time.

Your challenge:

  • Explain why a template is more reliable than console steps or a long script.
  • Compare the imperative and the declarative approach to building infrastructure.
  • Name the ways to deploy AWS infrastructure.

1.1 Why Infrastructure as Code

  • Infrastructure as code (IaC) means that you define infrastructure in files, and a tool builds it from them.
  • Building a VPC with the AWS CLI takes many commands that run in the right order, for example to create the VPC, the internet gateway, each subnet, each route table, and the NAT gateway.
  • The same work with the AWS SDK for Python (boto3) is a script of many API calls, and it has to handle the order and the errors itself.
  • Manual setup in the console adds a third problem: nothing records what was done, so the next environment differs.
  • Files can be stored in Git, reviewed by a second person, and run again, so each environment is built from the same description.

1.2 Imperative and Declarative Approaches

  • Both the CLI and the SDK are imperative: you list the steps.
  • A template is declarative: you describe the result, and the service works out the steps.
FeatureImperative (CLI and SDK scripts)Declarative (CloudFormation template)

Who works out the orderYou, in the script.The service.
ErrorsYour script has to handle them.The service handles them, and it can roll back.
What you manage afterwardSeparate resources.A stack that you update and delete as a group.

2. AWS CloudFormation

Problem Statement

The architects have chosen CloudFormation for FlashCart. The team asks what it does that a script does not, what a stack is, how it helps when many people share the same templates, and what it costs.

Your challenge:

  • Describe what CloudFormation is, and what a stack is.
  • List the benefits of CloudFormation.
  • State what CloudFormation costs.

2.1 Overview of CloudFormation

  • AWS CloudFormation is a declarative way of outlining your AWS infrastructure for any resources.
  • In one template you can say that you want a VPC and subnets, an internet gateway attached to the VPC, a security group, and two EC2 instances that use the security group in the new subnet.
  • CloudFormation then creates those resources in the right order, in parallel where it can, and with the exact configuration that you specify.
  • You write the template in YAML or JSON. The resources that CloudFormation creates from one template are managed together as a stack.
  • CloudFormation can also manage third-party resources through the CloudFormation registry, which is why its pricing page separates AWS resource types from third-party resource providers.

For example, within a CloudFormation template, you say:

  • I want a VPC and subnets.
  • I want an internet gateway, and I want it attached to the VPC.
  • I want a security group.
  • I want two EC2 instances that use this security group, in the subnet that was just created.
  • I want an S3 bucket.
  • I want a load balancer (ELB) in front of these machines.

Then CloudFormation creates those for you, in the right order, possibly in parallel and with the exact configuration that you specify.

2.2 Benefits of CloudFormation

  • Resources are created and deleted automatically, so there are no manual errors.
  • Resources are created and deleted as a group, called a stack, so no ghost resources remain when you delete the stack.
  • Resources that do not depend on each other are created in parallel, which speeds up deployment.
  • The same template can be deployed in different Regions or accounts with few or no changes, and teams can share it.
  • The template can be version controlled with a tool such as Git, so it is easy to return to an earlier deployment.
  • AWS Infrastructure Composer lets you build a template visually, with drag and drop.

2.4 Pricing

  • There is no additional charge for using CloudFormation with resource types in the AWS::* and Alexa::* namespaces. You pay for the AWS resources that the stack creates, as if you had created them by hand.
  • Third-party resource providers and custom hooks are charged per handler operation, and a free tier covers the first 1,000 handler operations each month. Check the CloudFormation pricing page for current prices.

3. Template Anatomy and Parameters

Problem Statement

FlashCart wants one template for both environments. In dev, the server is a small instance and has no extra tags. In prod, the server is larger and carries a Critical tag. The team also wants the address of the server to be shown after the stack is built.

The new orders database needs a master password. The security team does not want the password in the template, in Git, or in the stack events, and the team wants to know how big one template can get before it must be split.

  • Name the sections of a template, and the only one that is required.

3.1 Template Structure

  • A template is a YAML or JSON file. Only the Resources section is mandatory.
  • Each section has one job. Do not repeat a major section such as Resources: CloudFormation might accept the template, but its behavior is undefined.

A template has several major sections, and Resources is the only required one. Some sections can appear in any order. As you build a template, though, it helps to follow the logical order of the sections in the table below, because values in one section can refer to values in an earlier section.

3.1.2 Example: Template Launches an EC2 Instance

This sample template launches an EC2 instance whose size and tags depend on the Env parameter (dev or prod), attaches an Elastic IP address to it, and returns that address as an output.

AWSTemplateFormatVersion: "2010-09-09"
Description: Sample CloudFormation template for SAA exam preparation

Metadata:
  Author: Chetan
  Purpose: Demonstrate CFN Template sections

Parameters:
  Env:
    Type: String
    Default: dev
    AllowedValues: [dev, prod]
    Description: Deployment environment

Mappings:
  InstanceConfig:
    dev:  { InstanceType: t2.micro }
    prod: { InstanceType: t3.small }

Conditions:
  IsProd: !Equals [ !Ref Env, prod ]

Resources:
  EC2Instance:
    Type: AWS::EC2::Instance
    Properties:
      ImageId: ami-0abcdef1234567890
      InstanceType: !FindInMap [ InstanceConfig, !Ref Env, InstanceType ]
      Tags:
        - Key: Name
          Value: !Sub "${Env}-ec2"
        - Key: Environment
          Value: !Ref Env
        - !If
          - IsProd
          - { Key: Critical, Value: "true" }
          - !Ref AWS::NoValue
  ElasticIP:
    Type: AWS::EC2::EIP
    Properties:
      Domain: vpc
  EIPAssociation:
    Type: AWS::EC2::EIPAssociation
    Properties:
      InstanceId: !Ref EC2Instance
      EIP: !Ref ElasticIP

Outputs:
  ElasticIP:
    Description: Elastic IP address
    Value: !Ref ElasticIP

3.2 Parameters in Detail

  • Parameters let you input custom values each time you create or update a stack, so one template fits many cases.
  • The only required attribute of a parameter is Type. A Description of up to 4,000 characters appears in the Create Stack wizard.
  • If you omit Default, you must give a value when you create the stack. Without one, stack creation fails with the error “Parameters: [KeyName] must have values”.
  • A default must satisfy the parameter’s own constraints, and a constraint does not make a required value valid: it only checks it.
  • A template can have up to 200 parameters. Each one needs a unique, alphanumeric logical ID.
  • You can reference parameters from the Resources and Outputs sections of the same template, with the Ref function.
  • By default, the console lists parameters in alphabetical order. The AWS::CloudFormation::Interface metadata key groups related parameters.

3.3 Keeping Secrets Out of Templates

  • NoEcho masks a parameter value as asterisks (*****) in calls that describe the stack or its events, in the console, the command line tools, and the API.
  • NoEcho does not mask values in the Metadata section, in the Outputs section, or in the Metadata attribute of a resource. AWS strongly recommends that you do not put passwords or secrets there.
  • Do not use a NoEcho parameter, or any sensitive value, in a resource property that is part of the resource’s primary identifier. CloudFormation might then use the plaintext value in the resource ID, and it can appear in outputs.
  • The better practice is a dynamic reference: the template holds a pointer, and CloudFormation reads the value from another service when it needs it.
Dynamic referenceGets the value fromSyntax
ssmA plaintext value in AWS Systems Manager Parameter Store.{{resolve:ssm:parameter-name:version}}
ssm-secureA secure string in AWS Systems Manager Parameter Store.{{resolve:ssm-secure:parameter-name:version}}
secretsmanagerA whole secret, or a value inside a secret, in AWS Secrets Manager.{{resolve:secretsmanager:secret-id:SecretString:json-key:version-stage:version-id}}
 
MasterUsername: "{{resolve:ssm:/flashcart/db/username}}"
MasterUserPassword: "{{resolve:secretsmanager:flashcart/db/master:SecretString:password}}"
  • A template can contain up to 60 dynamic references.
  • Dynamic references are not supported in AWS::CloudFormation::Init metadata and in the EC2 UserData property.
  • A dynamic reference cannot supply a secure value to a custom resource.
  • Do not use a dynamic reference or a secret in a property that is part of a resource’s primary identifier.
  • The two examples above were written for this course. The parameter and secret names are placeholders.

3.4 Outputs and Cross-Stack References

  • The Outputs section returns values when you view the stack, for example an address or a resource ID.
  • An output can be exported with a name, and another stack can import it with Fn::ImportValue.
  • Export names must be unique for each account within a Region.
  • Cross-stack references are limited to the same account and the same Region.
  • After another stack imports an exported value, you cannot delete the exporting stack or change the exported value. You must remove all the imports first.

4.3 Dependencies and Resource Attributes

  • CloudFormation works out the order from the references between resources. A resource that uses Ref or Fn::GetAtt on another resource is created after it, and resources with no link are created in parallel.
  • The DependsOn attribute adds an explicit dependency when no reference exists.
  • A CreationPolicy attribute makes CloudFormation wait until a resource, such as an EC2 instance or an Auto Scaling group, sends the required success signals. The instance runs the cfn-signal helper script when its software is installed.
  • If the signals do not arrive before the timeout, CloudFormation treats the creation as failed and rolls the stack back.
  • For EC2 and Auto Scaling resources, AWS recommends a CreationPolicy instead of a wait condition. A wait condition works for signals from outside the stack.
  • The DeletionPolicy and UpdateReplacePolicy attributes control what happens when a resource is deleted or replaced (tab 7).
Resources:
  WebServer:
    Type: AWS::EC2::Instance
    CreationPolicy:
      ResourceSignal:
        Timeout: PT5M
    Properties:
      # ... the instance runs cfn-signal when its software is installed
  • This sample was written for this course. The timeout uses the ISO 8601 format, and PT5M means five minutes.

4.4 What Is a Stack

  • A stack is a collection of AWS resources that you manage as a single unit. The template defines the collection, and CloudFormation creates and deletes all the member resources of the stack together, and manages the dependencies between them for you.
  • You create, update, and delete a collection of resources by creating, updating, and deleting the stack.
  • A template is the blueprint, and a stack is what CloudFormation builds from it. One template can create many stacks, for example one each for dev, test, and prod, with different parameter values.
  • A stack lives in one account and one Region. Its name must be unique in the Region where you create it, and CloudFormation gives it a unique stack ID, which is an Amazon Resource Name (ARN).

Problem Statement

FlashCart’s single production template now has more than 400 resources, and three teams edit it. A change to the network can break a database. The company also has separate AWS accounts for dev, test, and prod, and the security team wants the same IAM roles and AWS Config rules in every account and Region, including accounts that join the organization later.

Your challenge:

  • Explain how to split one large template into reusable parts.
  • Explain how to deploy the same template to many accounts and Regions, and how to control the rollout.
  • Decide between nested stacks, cross-stack references, and StackSets for each need.

5.1 Nested Stacks

  • A parent stack creates and manages one or more nested (child) stacks.
  • Nested stacks help organize templates into reusable, modular components, and they can help work around CloudFormation’s per-template size and resource limits.
  • Common uses include organizing resources into networking, compute, and database layers, and reusing templates for components such as VPCs, IAM resources, and security baselines.
  • In the parent template, declare a child stack with the AWS::CloudFormation::Stack resource type, and provide its template URL in Amazon S3. The parent can pass parameters to the child, and it can access the child’s outputs with Fn::GetAtt, such as Outputs.OutputName.
  • When you update a parent stack, CloudFormation initiates an update for each nested stack to check for changes. It updates resources only in the nested stacks whose templates changed.
  • A nested stack hierarchy can contain more than 2,500 resources in total, but a single operation cannot create, update, or delete more than 2,500 resources.
  • To preview changes across the stack hierarchy, create a change set with IncludeNestedStacks set to true.
  • Configure termination protection on the root stack. It applies to the nested stacks, and you cannot change it directly on a nested stack. To continue a failed rollback in a nested stack, run the operation on its parent stack, which is the stack that contains the nested stack resource.

Nested stacks can contain other nested stacks, forming a hierarchy. The root stack is the top-level stack in the hierarchy. Each nested stack has an immediate parent stack. For first-level nested stacks, the root stack is also the parent.

  • Stack A is the root stack.
  • Stack B is a child of stack A, so stack A is both its parent and its root stack.
  • Stack C is a child of stack B.
  • Stack D is a child of stack C.

6. Updating Stacks and Detecting Drift

Problem Statement

Before FlashCart changes the production database template, the architects want to see what will be replaced and what will only be modified. They also want to make sure that nobody can replace the orders database by accident in a future update. Last month, an engineer opened a security group in the console to test a problem and never closed it, so the live stack no longer matched the template. Finally, the old payment queue was created by hand, and the team wants CloudFormation to manage it.

Your challenge:

  • Predict whether an update modifies or replaces a resource.
  • Preview an update, and block updates to critical resources.
  • Find manual changes, and bring an existing resource under CloudFormation.

6.1 Update Behaviors

  • When you submit an update, CloudFormation compares the new template with the current one and changes only what differs. Resources that did not change keep running.
  • Each property has one of three update behaviors, which the resource reference documents for that property.
Update behaviorWhat happensPhysical ID
Update with no interruptionCloudFormation updates the resource without disrupting it.Stays the same.
Update with some interruptionCloudFormation updates the resource with some interruption. An EC2 instance might be unavailable while it is reconfigured.Stays the same.
ReplacementCloudFormation recreates the resource. It usually creates the replacement first, points dependent resources at it, and then deletes the old resource.A new physical ID.
  • Changing a property that requires replacement is an update even when the real value does not change.
  • Plan a replacement of a database before you update, because the new resource starts empty.
  • Do not change stack resources outside CloudFormation. A mismatch between the template and the real resources can cause errors when you update or delete the stack.

6.2 Change Sets

  • A change set lets you preview the changes before you update a stack.
  • It shows which resources will be added, modified, or deleted.
  • It helps you avoid unintended resource replacement or deletion.
  • It does not change anything until you explicitly execute it.
  • A change set has a type: CREATE for a new stack, UPDATE for an existing stack, and IMPORT for an import operation. A new stack from a CREATE change set stays in the REVIEW_IN_PROGRESS status until you execute the change set.
  • Set IncludeNestedStacks to true to preview the changes of the entire nested stack hierarchy.

6.3 Stack Policies

  • When you create a stack, all update actions are allowed on all resources, and anyone with stack update permissions can update all of them.
  • A stack policy is a JSON document that defines which update actions are allowed on which resources. You set it on the stack, and it applies to everyone who updates the stack.
  • A stack policy protects critical resources, such as a database, from being updated, replaced, or deleted by accident during a stack update.
  • When an update changes a resource, CloudFormation also updates the resources that depend on it. If a stack policy protects those resources, you need permission to update them.
{
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "Update:*",
      "Principal": "*",
      "Resource": "*"
    },
    {
      "Effect": "Deny",
      "Action": ["Update:Replace", "Update:Delete"],
      "Principal": "*",
      "Resource": "LogicalResourceId/OrdersDatabase"
    }
  ]
}
  • This policy was written for this course. It allows all updates, and it denies the actions that replace or delete the resource with the logical ID OrdersDatabase.

6.4 Drift Detection

  • Drift detection identifies manual changes made outside CloudFormation.
  • It compares the actual resource configuration with the template, including the values of the template parameters.
  • For each resource it reports IN_SYNC, MODIFIED, DELETED, or NOT_CHECKED. The slides list only IN_SYNC and MODIFIED. A resource that was deleted outside CloudFormation shows as DELETED, and a resource type that does not support drift detection shows as NOT_CHECKED.
  • For the stack it reports DRIFTED when one or more resources have drifted, IN_SYNC when none have, and NOT_CHECKED before the first check.
  • Drift detection only reports. It does not fix the difference. To fix it, update the template, or change the resource back to match the template.
  • Drift detection helps you enforce IaC discipline: all changes go through the template.

6.5 Bringing Existing Resources Under CloudFormation

  • You can import existing resources into a stack. You describe them in a template that includes both the resources already in the stack and the resources to import, and then you create an IMPORT change set.
  • The import operation fails if you modify existing parameters in a way that creates, updates, or deletes a resource.
  • After an import, run drift detection to check that the resource matches the template.
  • The IaC generator scans the resources in your account and Region that CloudFormation does not manage, and it generates a template that you can use to import them or to replicate them in a new account.

7.1 Automatic Rollback

  • Rollback occurs automatically if stack creation or update fails.
  • During rollback, CloudFormation tries to return the stack to the last known stable state.
  • For a failed stack creation, all the resources that were created successfully are deleted by default.
  • You can disable rollback during stack creation. This is useful for troubleshooting, because the resources that were created stay in place so that you can inspect them.

ROLLBACK_COMPLETEA stack creation failed, and CloudFormation rolled it back.The stack cannot be updated. Delete it, fix the template, and create a new stack.
UPDATE_ROLLBACK_COMPLETEA stack update failed, and the rollback to the last stable state succeeded.Fix the cause, and update again.
UPDATE_ROLLBACK_FAILEDCloudFormation could not roll back all the changes after a failed update, for example because a database that it needs was deleted outside CloudFormation.Fix the cause, and run ContinueUpdateRollback.
DELETE_FAILEDCloudFormation could not delete the stack or one of its resources.Check the stack events, fix the cause, and delete the stack again.

7.1.1 Continue Update Rollback

  • The ContinueUpdateRollback operation moves a stack from UPDATE_ROLLBACK_FAILED to UPDATE_ROLLBACK_COMPLETE.
  • If a resource cannot be rolled back, you can list it in ResourcesToSkip. CloudFormation sets the status of the skipped resources to UPDATE_COMPLETE and continues. Skip only the minimum number of resources that you need.
  • Before the next update, bring the stack and the skipped resources back into agreement.
  • For nested stacks, run the operation on the parent stack, and not on the nested stack.

  • The DeletionPolicy attribute controls what CloudFormation does to a resource when its stack is deleted. You set it on each resource.

DeleteThe resource is deleted. This is the default.

  • Some resource types have a different default. For an AWS::RDS::DBCluster, and for an AWS::RDS::DBInstance without a DBClusterIdentifier, the default policy is Snapshot.
  • The UpdateReplacePolicy attribute does the same job for the old resource when an update replaces it. It accepts Delete, Retain, and Snapshot. If you choose Snapshot for a resource type that does not support snapshots, CloudFormation uses Delete.
  • With a Retain policy, CloudFormation removes the retained resource from its scope. It stays in your account and you pay for it until you delete it yourself.

7.3 Termination Protection

  • Termination protection stops a stack from being deleted by accident. If someone tries to delete a stack with termination protection on, the operation fails and the stack stays unchanged.
  • Termination protection is off by default. You can turn it on when you create the stack, and edit it later.
  • For a nested stack, termination protection is set on the root stack.
  • Termination protection protects the stack. It does not protect a single resource from a replacement or from being removed from the template. Use DeletionPolicy, UpdateReplacePolicy, and a stack policy for those cases.

7.4 IAM Service Role

  • CloudFormation does not have permissions by default to create resources.
  • By default, CloudFormation uses a temporary session that it builds from the credentials of the user or role that runs the operation.
  • If you specify a CloudFormation service role when you create the stack, CloudFormation uses that role for all operations on that stack. The role must trust cloudformation.amazonaws.com.
  • The iam:PassRole permission allows an IAM principal to pass a service role to CloudFormation, so a person must have it for the roles that they are allowed to use.
  • The user must have the iam:PassRole permission for the service role to create or update a stack with it.
  • If CloudFormation must create resources that need another IAM role, for example an EC2 instance with an instance profile, the service role also needs iam:PassRole permissions.
  • A service role lets a person create stacks with only the permissions to use CloudFormation and to pass the role, and not the permissions to create every resource.
  • Risk: other users who can run operations on the stack can use its service role, even without the iam:PassRole permission. A role with more permissions than they should have can unintentionally escalate their permissions, so apply least privilege to the role.

10.1 What Is AWS CloudFormation Git Sync

  • AWS CloudFormation Git sync is a native CloudFormation feature that lets you manage, deploy, and update your stacks directly from a Git repository.
  • You configure CloudFormation to monitor a Git repository. The repository is monitored for changes to two files: a CloudFormation template file that defines a stack, and a stack deployment file that holds the parameters for the stack.
  • When you commit a change to the template or to the deployment file, CloudFormation updates the stack automatically.
  • It removes the need to build and maintain a deployment pipeline, such as AWS CodePipeline or GitHub Actions, just to update your CloudFormation stacks.
  • With pull requests and version tracking, you can configure, deploy, and update your stacks from one place. If you turn it on, CloudFormation can leave a comment on a pull request that explains what changes will be made to the stack before it updates it.
  • Git sync gives you a console interface to link a repository, generate a stack deployment file, update a template, and submit a pull request to your repository. It also gives you a status dashboard to monitor, edit, and troubleshoot your Git sync deployments.
  • You reach Git sync in the CloudFormation console when you create a stack. You can also reach it through AWS CodeConnections.
  • Git sync supports GitHub, GitHub Enterprise, GitLab, Bitbucket, and GitLab self-managed repositories. It is available in selected AWS Regions, so check the documentation for yours.

10.3 How It Works

  1. You connect your Git provider to CloudFormation with AWS CodeConnections.
  2. You create a template that defines your stack, and add it to the repository.
  3. In the CloudFormation console, you create a stack and choose Sync from Git. You choose the repository, the branch, and the template.
  4. You provide your own stack deployment file, or Git sync generates one and submits it to your repository.
  5. Git sync creates a pull request in your repository to sync the stack with the template file and the deployment file.
  6. You merge the pull request. CloudFormation then provisions the stack, configures it with your deployment parameters, and starts to monitor the repository.
  7. From then on, CloudFormation detects every commit to the template file or the deployment file. If your team uses pull requests, the team reviews and approves the change first. When it is accepted, CloudFormation deploys it.
  8. You monitor the status and the history of commits in the console.

AWS recommends the aws:SourceAccount and aws:SourceArn condition keys to prevent the confused deputy problem.
Permissions for the console userThe person who sets up Git sync needs codeconnections permissions to create and manage the repository link and the sync configuration, and cloudformation permissions to view and manage stacks.

10.5 Create a Stack With Git Sync

  1. Open the CloudFormation console, and choose the Region for the stack.
  2. On the Stacks page, choose Create stack, and then choose With new resources (standard).
  3. For Prerequisite - Prepare template, keep Choose an existing template. For Specify template, choose Sync from Git, and choose Next.
  4. On the Specify stack details page, type a stack name. Stack names can include letters, numbers, and dashes.
  5. For Stack deployment file, choose to have the file created and placed in your repository, or choose that you provide your own file.
  6. For Template definition repository, choose a linked Git repository, or link a new one. If you link one, choose the repository provider and the connection. If no connection appears, add a new connection in the Connections console.
  7. Choose the Repository and the Branch that Git sync must monitor.
  8. Enter the Deployment file path, from the root of the branch, including the file name.
  9. Choose an IAM role: a new role, or an existing one.
  10. Choose whether to keep Enable comment on pull request on. When it is on, CloudFormation posts the change set information in pull requests for stack updates.
  11. Enter the Template file path, from the root of the repository.
  12. Optionally add parameters and tags, and choose Next. Set the stack options, and choose Next.
  13. Review the settings. Check that the stack is set to Sync from Git, and that the repository, the branch, and the preview of the deployment file are correct.
  14. Choose Submit. A pull request is created in your repository. You must merge it to create the stack. After that, CloudFormation monitors the repository for changes.
  • The console labels can change. If a label is different, use the closest match.

10.6 Update and Monitor the Stack

  • To update the stack, change the template file or the stack deployment file in the repository, and commit the change to the monitored branch. CloudFormation updates the stack automatically.
  • With pull requests, your team can review a change before it reaches the monitored branch. With comments turned on, CloudFormation adds a summary of the stack changes to the pull request, so reviewers can see the impact before they merge.
  • To see the status, select the stack and choose the Git sync tab. It has two panels: Git sync status and Latest sync events.

10.8 Day-to-Day Tips

  • Turn on Enable comment on pull request, and protect the monitored branch so that every change needs a review (Lesson 296.3).
  • Keep one stack deployment file for each environment, for example one for dev and one for prod, so that the parameters of each environment are reviewed like code.
  • Make sure that you configured the right repository and branch. A commit to another branch does not update the stack.
  • To undo a bad change, revert the commit, and let Git sync deploy the earlier template. CloudFormation also rolls back a failed update by itself.
  • When a sync fails, read the Git sync status message and the sync events, then the stack events.

11.3 Lesson Summary

  • Infrastructure as code defines infrastructure in files. CloudFormation is the AWS-native, declarative service for it, with YAML or JSON templates and stacks that are created and deleted as a group.
  • A template has an optional header and Parameters, Rules, Mappings, Conditions, Transform, Resources (mandatory), and Outputs. Intrinsic functions and pseudo parameters connect them. Dynamic references keep secrets out of the template.
  • References set the creation order, DependsOn forces it, and a CreationPolicy waits for signals. Templates with IAM resources need a capability.
  • Nested stacks split one large template into reusable parts in one account and Region. StackSets deploy one template to many accounts and Regions, with permission models and deployment options.
  • Updates modify or replace resources. Change sets preview an update, stack policies block denied update actions, and drift detection finds changes made outside CloudFormation. Import and the IaC generator bring existing resources under CloudFormation.
  • A failed stack rolls back automatically. DeletionPolicy controls what happens to a resource when its stack is deleted, termination protection stops the stack from being deleted, and a service role gives CloudFormation its own permissions.

12. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: Explain what infrastructure as code is, and compare CloudFormation with the AWS CLI and the AWS SDK.

Maps to: Objective 1 (Knowledge).

Infrastructure as code defines infrastructure in files that a tool turns into resources. The AWS CLI and the AWS SDK are imperative: you list the steps, their order, and the error handling. CloudFormation is declarative: a YAML or JSON template describes the desired state, and CloudFormation creates the resources in the right order, in parallel where possible, and manages them as a stack that is deleted as a group.

Question 2: Name the sections of a CloudFormation template, and explain the life cycle of a stack.

Maps to: Objective 2 (Comprehension).

The sections are the format version, Description, Metadata, Parameters, Rules, Mappings, Conditions, Transform, Resources, and Outputs, with Resources as the only mandatory one. You upload the template to Amazon S3 or the console, create a stack with a name and parameters, and CloudFormation creates the resources and records events. You update the stack with a new template, and deleting the stack deletes the resources as a group.

Question 3: Show how one template can serve dev and prod, with a different instance size and a tag only in prod.

Maps to: Objective 3 (Application).

Add an Env parameter with allowed values dev and prod. Add a mapping from each environment to an instance type, and read it with Fn::FindInMap and Ref. Add an IsProd condition with Fn::Equals, and use Fn::If with AWS::NoValue to add the Critical tag only when the condition is true. An Outputs section can return the address of the server.

Question 4: A template needs a database password. Explain why NoEcho is not enough, and what you use instead.

Maps to: Objective 3 (Application).

NoEcho masks a parameter value in stack descriptions and events, but it does not mask values in the Metadata section, the Outputs section, or the Metadata attribute of a resource, and AWS recommends that you do not put secrets there. A dynamic reference to AWS Secrets Manager or to a Systems Manager Parameter Store secure string keeps the secret outside the template, and CloudFormation reads it when it needs it. Dynamic references are not supported in UserData or in AWS::CloudFormation::Init metadata.

Question 5: Compare nested stacks, cross-stack references, and StackSets, and say when you use each.

Maps to: Objective 4 (Application).

Nested stacks are child stacks that a parent stack manages in one account and Region, and they help with modularity and size limits. Cross-stack references let independent stacks share an exported output in the same account and Region, and they block deleting the exporting stack while it is imported. StackSets deploy the same stack to many accounts and Regions from an administrator account, with self-managed or service-managed permissions, automatic deployment, and controls such as failure tolerance and Region concurrency.

Question 6: Compare change sets, stack policies, and drift detection.

Maps to: Objective 5 (Analysis).

A change set previews an update by showing which resources will be added, modified, replaced, or deleted, and applies nothing until it is executed. A stack policy is a JSON document that blocks the update actions that you deny on the resources that you name, for everyone who updates the stack. Drift detection compares the actual configuration with the template, reports each resource as IN_SYNC, MODIFIED, DELETED, or NOT_CHECKED and the stack as DRIFTED when any resource has drifted, and repairs nothing.

Question 7: A stack with an RDS database fails halfway, and the rollback fails too. Explain what you do, and how you protect the database in the future.

Maps to: Objective 6 (Evaluation).

A failed creation rolls back automatically and deletes the new resources, unless you disabled rollback to troubleshoot. If an update rollback fails, the stack is in UPDATE_ROLLBACK_FAILED, and you fix the cause and run ContinueUpdateRollback, skipping the minimum number of resources that cannot be rolled back. To protect the database, set DeletionPolicy and UpdateReplacePolicy to Retain or Snapshot, attach a stack policy that denies Update:Replace and Update:Delete on it, and turn on termination protection for the stack.

Question 8: Explain how a service role works, what iam:PassRole does, and what risk a service role carries.

Maps to: Objective 6 (Evaluation).

Without a service role, CloudFormation uses a temporary session built from the credentials of the person who runs the operation. With a service role, CloudFormation uses that role for all operations on the stack, so the person needs only the permission to use CloudFormation and iam:PassRole for that role. The risk is that other users who can run operations on the stack can use the role even without iam:PassRole, so a role with excess permissions can escalate their access. Apply least privilege to the role.

Question 9: A team has resources that were created by hand. Explain two ways to bring them under CloudFormation.

Maps to: Objective 6 (Evaluation).

You can import the resources into a stack. You describe them in a template that includes the resources already in the stack and the resources to import, create an IMPORT change set, execute it, and then run drift detection to confirm that the resources match the template. You can also use the IaC generator, which scans the resources that CloudFormation does not manage and generates a template that you can use to import them or to replicate them in a new account.

Question 10: Design a secure, multi-environment CloudFormation deployment for FlashCart’s network and application, with dev, test, and prod accounts.

Maps to: Objective 7 (Synthesis).

Store versioned templates in Git, and split them into nested stacks for the network, compute, and database layers, with parameters, mappings, and conditions for the differences between environments, and dynamic references for secrets. Use StackSets with service-managed permissions and automatic deployment for the baseline IAM roles and Config rules in every account. Preview each production update with a change set, protect the data stores with DeletionPolicy, UpdateReplacePolicy, and a stack policy, turn on termination protection, run drift detection regularly, and create stacks with a least-privilege service role.
