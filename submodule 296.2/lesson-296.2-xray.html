1. Why Distributed Tracing

Problem Statement

FlashCart’s checkout takes eight seconds for some customers, and two seconds for others. A checkout request goes through the web front end, the order service, the billing and payment service, a database, and an email service. Each team looks at its own logs and says that its part is fast.

The architects ask for a way to follow one request from the first service to the last, and to see how long each step took.

Your challenge:

  • Explain why logs and metrics alone do not find the slow service.
  • Describe what AWS X-Ray collects and what the team can do with it.
  • List the questions that X-Ray answers.

1.1 The Problem With Distributed Applications

  • A modern application is split into many services, often owned by different teams. One user request can call several of them.
  • When the request is slow or fails, the cause can be in any service, or in a call between two services.
  • Logs are kept separately by each service, so nobody sees the whole path of one request.
  • You need a tool that captures the trace of the request as it goes from one service to the next.

1.2 Logs, Metrics, and Traces

SignalThe question it answersAWS service
LogsWhat happened in this service?Amazon CloudWatch Logs
MetricsHow much, how often, and how fast is this resource working?Amazon CloudWatch metrics and alarms
TracesWhere did this one request spend its time across all the services?AWS X-Ray

1.3 What AWS X-Ray Is

  • AWS X-Ray is a service that collects data about the requests that your application serves.
  • It provides tools that you can use to view, filter, and gain insights into that data, to identify issues and opportunities for optimization.
  • It works with applications on Amazon EC2, Amazon ECS, AWS Lambda, and AWS Elastic Beanstalk, and with other AWS services that send trace data.
  • It gives you a visual map of your application, and a detailed timeline for each traced request.

1.4 What You Use X-Ray For

  • Debugging slow responses to user requests.
  • Troubleshooting increased error rates.
  • Tracing the path of a user request, which is called a trace.
  • Checking whether requests are completed within the service level agreement time.
  • Finding which service is the bottleneck in the application.
  • Finding which users are affected by a service disruption.

2. AWS X-Ray Concepts

Problem Statement

FlashCart’s engineers see words such as trace, segment, subsegment, and annotation in the console. Support also asks for one thing: show every checkout request from the “gold” customer tier that took longer than five seconds, so that the team can see which service was slow.

The finance team adds a worry: tracing every request of a busy site would be expensive.

Your challenge:

  • Explain how a trace, a segment, and a subsegment relate to each other.
  • Choose between an annotation and metadata to make the gold-tier requests searchable.
  • Explain how sampling keeps the cost of tracing under control.

2.1 Traces, Segments, and Subsegments

  • X-Ray receives data from services as segments, and it groups the segments that belong to one request into a trace.
  • The compute resources that run your application logic send data about their work as segments. A segment gives the name of the resource, details about the request, and details about the work done.
  • A segment can break its work down into subsegments. A subsegment gives more detailed timing, and records a downstream call that your application made, for example to an AWS service, an HTTP API, or a SQL database.
  • You can define your own subsegments to time a function or a block of code.
  • A trace ID tracks the path of one request. A trace collects all the segments that the request generated.
  • For a service that does not send its own segments, such as Amazon DynamoDB, X-Ray builds an inferred segment from the subsegment of the service that called it. You still see the dependency on the map.
  • A segment document can be up to 64 kB.
Segment dataExamples
The hostHostname, alias, or IP address.
The requestMethod, client address, path, and user agent.
The responseStatus and content.
The work doneStart and end times, and subsegments.
Issues that occurErrors, faults, and exceptions, including the exception stack.

2.2 The Service Graph and the Service Map

  • X-Ray uses the data that your application sends to build a service graph. Each AWS resource that sends data appears as a service, or node. Edges connect the services that work together to serve requests.
  • The console draws the graph as a service map, with timing and error information on each node.
  • For a distributed application, X-Ray combines the nodes of all the services that process requests with the same trace ID into one graph.

2.3 Annotations and Metadata

  • When you instrument an application, the SDK records the incoming and outgoing requests, the AWS resources used, and the application itself. You can add more information as annotations and metadata, on any segment or subsegment.
FeatureAnnotationsMetadata
What they areSimple key-value pairs.Key-value pairs whose values can be of any type, including objects and lists.
Indexed for searchYes. They work with filter expressions.No.
LimitX-Ray indexes up to 50 annotations per trace.Any size, as long as the segment document stays within 64 kB.
Use them toFind and group traces, for example by customer tier.Store extra detail that you view but do not search.
  • For FlashCart’s support request, record the customer tier as an annotation, so that the console can find the gold-tier traces.

2.4 Errors, Faults, and Throttles

CategoryWhat it means
ErrorClient errors, the 400 series.
FaultServer faults, the 500 series.
ThrottleThrottling errors, 429 Too Many Requests.

2.5 The Tracing Header

  • The trace ID and the sampling decision travel with the request in an HTTP header named X-Amzn-Trace-Id.
  • The first X-Ray-integrated service that the request reaches adds the header, and each service passes it downstream.
  • The header can also carry the ID of a parent segment, so that two connected requests can be linked.
X-Amzn-Trace-Id: Root=1-5759e988-bd862e3fe1be46a994272793;Parent=53995c3f42cd8ad8;Sampled=1
  • Root is the trace ID, Parent is the parent segment, and Sampled=1 means that the request is traced.
  • A user can add a tracing header to a request. An application can remove X-Amzn-Trace-Id from incoming requests to prevent that.
  • When a load balancer forwards a request, X-Ray takes the client IP address from the X-Forwarded-For header. That value can be forged, so do not trust it.

2.6 Sampling

  • Tracing every request of a busy application is costly, so the X-Ray SDK uses a sampling algorithm to decide which requests to trace.
  • By default, the SDK records the first request each second, and five percent of any additional requests. The default is conservative, to avoid charges when you start.
  • You can change the default rule, and add rules that match the properties of a service or a request, for example the URL path or the HTTP method.
  • You might trace every request of calls that change state or handle users and transactions, and sample health checks and background polling at a low rate.
Sampling rule settingWhat it does
PriorityThe order in which rules are evaluated, from 1 to 9999.
Reservoir sizeA fixed number of matching requests to trace each second, before the fixed rate applies.
Fixed rateThe share of matching requests to trace after the reservoir is used, from 0 to 1.
Match fieldsService name, service type, host, HTTP method, URL path, and resource ARN.
 
Resources:
  CheckoutSamplingRule:
    Type: AWS::XRay::SamplingRule
    Properties:
      SamplingRule:
        RuleName: checkout-all-requests
        ResourceARN: "*"
        Priority: 10
        FixedRate: 1.0
        ReservoirSize: 5
        ServiceName: "*"
        ServiceType: "*"
        Host: "*"
        HTTPMethod: "POST"
        URLPath: "/checkout*"
        Version: 1
  • This sample is based on the example in the CloudFormation documentation. It traces every POST request to a path that starts with /checkout, with a reservoir of five requests each second. The names and values are examples.

2.7 Filter Expressions and Groups

  • A busy application generates a lot of trace data. You use filter expressions to find the traces that matter, for example the traces for a path, a user, or an annotation value.
  • A group extends a filter expression. Traces that match the expression are accepted into the group, which has its own service graph, trace summaries, and Amazon CloudWatch metrics.
  • X-Ray publishes the metrics for the number of traces that match each criterion to CloudWatch every minute.
  • Updating a group’s filter expression does not change data that is already recorded. It applies only to later traces.

2.8 Retention

  • X-Ray keeps trace data for 30 days, and it keeps service graph data for 30 days.

3. Instrumenting Applications

Problem Statement

FlashCart’s order function runs on AWS Lambda behind Amazon API Gateway. The catalog service runs in containers on Amazon ECS, and a legacy pricing application still runs on EC2 instances. The team wants one trace through all of them.

A developer also reads that the X-Ray SDKs and daemon are in maintenance mode, and asks whether the team should still use them.

Your challenge:

  • Describe how the trace data of each kind of compute reaches X-Ray.
  • Turn on tracing for Lambda and API Gateway.
  • Explain what the maintenance mode of the SDKs and daemon means, and what AWS recommends.

3.1 How Trace Data Reaches X-Ray

  • Your application code is instrumented with the X-Ray SDK, which is available for languages such as Java, .NET, and Node.js. The SDK records the incoming and outgoing requests.
  • The SDK sends the segments to the X-Ray daemon, a process that runs next to the application. The daemon listens for traffic on UDP port 2000 by default, batches the segments, and sends them to the X-Ray service.
  • You then view the service map and the traces in the console.

3.2 The SDK and Daemon Timeline, and OpenTelemetry

  • AWS X-Ray is moving to OpenTelemetry (OTel) as its primary instrumentation standard. OpenTelemetry is an open-source standard for tracing and observability.
  • OpenTelemetry uses spans instead of segments and subsegments.
  • You can send OpenTelemetry traces to X-Ray with the AWS Distro for OpenTelemetry (ADOT), or with native OpenTelemetry and the Amazon CloudWatch OTel endpoint. The console experience stays the same.
  • Since August 2025, X-Ray also accepts trace IDs created with OpenTelemetry or any other framework that follows the W3C Trace Context specification.
PhaseDatesWhat AWS provides
General availabilityUntil February 25, 2026The SDKs and daemon are fully supported, with regular releases.
Maintenance modeFebruary 25, 2026 to February 25, 2027Releases only for critical security issues. No new features.
End of supportFrom February 25, 2027No more updates or releases. Earlier releases stay available.
  • As of October 2026, the SDKs and the daemon are in maintenance mode. AWS recommends that you migrate to OpenTelemetry before February 25, 2027.
  • Older exam material and older courses still describe the SDK and the daemon, so know both ways.

3.3 AWS Services That Integrate With X-Ray

  • AWS describes four kinds of integration. Active instrumentation samples and instruments incoming requests. Passive instrumentation instruments requests that another service has already sampled. Request tracing adds a tracing header to incoming requests and passes it on. Tooling runs the X-Ray daemon for you.
ServiceHow it works with X-Ray
AWS LambdaActive and passive instrumentation of incoming requests. Lambda adds two nodes to the map: one for the Lambda service and one for your function.
Amazon API GatewayActive and passive instrumentation. API Gateway uses sampling rules to decide which requests to record, and adds a node for the stage to the map.
AWS Elastic BeanstalkTooling. It can run the daemon on the Java SE and Tomcat platforms, and you turn it on with the XRayEnabled option or in the console.
Application Load BalancerRequest tracing. The load balancer adds the trace ID to the request header before it sends the request to a target.
Amazon SNS and Amazon SQSPassive instrumentation, so a trace can continue through a topic or a queue.
Amazon EC2 and Amazon ECSYou instrument the application and run the daemon, or an OpenTelemetry collector, yourself. On ECS, you can run it as a sidecar container in the task.

3.4 Active Tracing for AWS Lambda

  • A Lambda function has a tracing mode. The default, PassThrough, records no segments. Active records the AWS::Lambda and AWS::Lambda::Function segments, for the invocations that are sampled.
  • The execution role must be allowed to send trace data: xray:PutTraceSegments and xray:PutTelemetryRecords. The managed policy AWSXRayDaemonWriteAccess carries both permissions.
  • The Lambda console adds the permissions when you turn on active tracing. When you use infrastructure as code, you attach the policy yourself.
  • Add the X-Ray SDK to your deployment package only if you want subsegments for your own code and downstream calls.
Resources:
  CheckoutRole:
    Type: AWS::IAM::Role
    Properties:
      AssumeRolePolicyDocument:
        Version: "2012-10-17"
        Statement:
          - Effect: Allow
            Principal: { Service: lambda.amazonaws.com }
            Action: sts:AssumeRole
      ManagedPolicyArns:
        - arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole
        - arn:aws:iam::aws:policy/AWSXRayDaemonWriteAccess
  CheckoutFunction:
    Type: AWS::Lambda::Function
    Properties:
      Role: !GetAtt CheckoutRole.Arn
      TracingConfig:
        Mode: Active
      # Handler, Runtime, and Code are omitted in this sample.
  • This sample was written for this course. In the AWS Serverless Application Model, the same setting is Tracing: Active.

3.5 Tracing for Amazon API Gateway

  • You turn on X-Ray tracing for an API Gateway stage. API Gateway then samples requests with the sampling rules, adds the tracing header, and puts a node for the stage on the service map.
  • In CloudFormation, the AWS::ApiGateway::Stage resource has the TracingEnabled property for this setting.
  • With Lambda behind the stage, the map shows the stage, the Lambda service, and the function as connected nodes.

4. Analyzing Traces, Security, and Cost

Problem Statement

FlashCart’s payments look slow, and the team suspects that a downstream service is throttling. The security team asks who can read traces, because traces can contain request details. Finance asks what tracing costs, and wants a way to be told when a service starts to fail more often.

Your challenge:

  • Find the slow or failing service on the service map, and list its traces.
  • Create a group that follows server faults.
  • Give the right permissions to the right people, and explain what tracing costs.

4.1 Reading the Service Map

  • Each node is a service or an AWS resource, and each edge is a call between two of them. A node shows average response time and request rate, and it flags errors, faults, and throttles.
  • Start from the node that looks slow or unhealthy, and open the traces that passed through it.
  • In a trace, the timeline shows each segment and subsegment, so you can see which step took the time.
  • For a downstream service that does not send segments, such as DynamoDB, the node comes from an inferred segment.
  • AWS documents the trace details page, with the segment and subsegment details, in the Amazon CloudWatch console. Annotations and metadata appear there.

4.2 Finding Traces With Filter Expressions

  • A filter expression lets you narrow the traces to the ones that you care about. You can combine conditions on the response time, on errors and faults, on annotations, on the URL, and on the user ID.
  • If your code records a user ID on a segment, you can find the traces for that user with the user keyword.
To findExample filter expression
Traces slower than five secondsresponsetime > 5
Traces with a server faultfault = true
Traces for one customer tierannotation.tier = "gold"
Traces for one URL pathhttp.url CONTAINS "/checkout"
  • These examples follow the filter expression syntax of the X-Ray console. Check the syntax reference before you use them.

4.3 Groups and Insights

  • A group saves a filter expression. It gives you its own service graph, trace summaries, and CloudWatch metrics, so that you can set an alarm on the number of matching traces.
  • X-Ray Insights turns on automatic anomaly detection for a group, and can send notifications. In CloudFormation, you set InsightsEnabled and NotificationsEnabled on the group.
  • Groups are billed by the number of retrieved traces that match the filter expression.
Resources:
  CheckoutFaultsGroup:
    Type: AWS::XRay::Group
    Properties:
      GroupName: checkout-faults
      FilterExpression: "fault = true"
      InsightsConfiguration:
        InsightsEnabled: true
        NotificationsEnabled: false
  • This sample was written for this course. It follows the properties of the AWS::XRay::Group resource.

4.4 Security

  • Sending trace data needs permission. The Put actions, xray:PutTraceSegments and xray:PutTelemetryRecords, are for the application. The managed policy AWSXRayDaemonWriteAccess carries them.
  • Reading traces uses the API actions that return the service graph and the traces, such as GetServiceGraph, GetTraceSummaries, and BatchGetTraces. Give read permission only to the people who need it, because traces describe requests.
  • X-Ray encrypts trace data at rest. You can use an AWS KMS key that you manage, instead of the default key, when your rules require it. You can also track changes to the X-Ray encryption configuration with AWS Config.
  • X-Ray API calls can be logged with AWS CloudTrail.
  • Do not put secrets in annotations, metadata, or user IDs.
  • Apply the advice about the tracing header from tab 2: remove X-Amzn-Trace-Id from incoming requests if you do not want users to set sampling decisions.

4.5 Cost

  • You pay for the traces that are recorded, retrieved, and scanned. Trace data is kept for 30 days at no extra cost.
  • X-Ray has a free tier each month, for the first 100,000 traces recorded and the first 1,000,000 traces retrieved or scanned. Check the pricing page for current prices.
  • Sampling is your main cost control. The default sampling rule is conservative, and you can lower or raise the rate for each kind of request.
  • Groups and Insights add to the traces that are retrieved or processed.

5.3 Exam Scenarios

Scenario 1

Written for this course.

Scenario: A serverless application uses API Gateway, Lambda, DynamoDB, and SNS. Users report that some requests take much longer than others, and the team cannot tell which part is slow.

Show Answer and Explanation

Answer: Turn on X-Ray tracing for the API Gateway stage, set the Lambda function’s tracing mode to Active with the X-Ray write permissions on its role, and read the service map and the traces. The map shows the node with the high latency, for example the SNS call, and the trace timeline shows the time of each step.

Scenario 2

Written for this course.

Scenario: A company runs containers on Amazon ECS and needs traces from the application code. The application is written in Java.

Show Answer and Explanation

Answer: Instrument the application, and run the X-Ray daemon, or an OpenTelemetry collector, as a sidecar container in the task, so that the application can send its trace data. Because the SDKs and the daemon are in maintenance mode, AWS recommends OpenTelemetry for new work.

Scenario 3

Written for this course.

Scenario: The cost of X-Ray is higher than expected for a busy website that traces all requests.

Show Answer and Explanation

Answer: Keep the default sampling rule, which traces the first request each second and five percent of the rest, and add sampling rules that trace every request only for the important paths, such as /checkout, and trace health checks at a low rate. Check the volume of traces that are retrieved and scanned by groups and Insights.

Scenario 4

Written for this course.

Scenario: The security team wants to know who changed the X-Ray encryption settings, and wants traces encrypted with a key that the company controls.

Show Answer and Explanation

Answer: Configure X-Ray to use an AWS KMS key that the company manages, and use AWS Config to track changes to the X-Ray encryption configuration. X-Ray API calls can also be logged with CloudTrail.

5.4 Lesson Summary

  • Distributed tracing follows one request across many services. AWS X-Ray collects the data, builds a service map, and shows a timeline for each trace.
  • A trace holds the segments of one request. Segments hold the work of a service, and subsegments hold downstream calls and blocks of code. Annotations are indexed and searchable, and metadata is not.
  • The tracing header X-Amzn-Trace-Id carries the trace ID and the sampling decision. By default, X-Ray traces the first request each second and five percent of the rest.
  • Lambda and API Gateway have built-in tracing. For Lambda, set the mode to Active and allow the X-Ray write actions. EC2 and ECS need the daemon or an OpenTelemetry collector.
  • The X-Ray SDKs and daemon are in maintenance mode until February 25, 2027, and AWS recommends OpenTelemetry.
  • Filter expressions find traces, groups count them and publish metrics, and Insights detects anomalies. Sampling controls cost, and data is kept for 30 days.

Memory Hook

Trace the request, read the map, sample to save money, and keep secrets out of the trace.

6. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: Explain why logs and metrics are not enough for a microservices application, and what a trace adds.

Maps to: Objective 1 (Knowledge).

Logs and metrics are kept for each service, so they show that something is slow or failing but not where in the path of a request. A trace follows one request from the first service to the last and shows how long each step took. AWS X-Ray collects that data, builds a service map, and shows a timeline for each traced request.

Question 2: Describe a trace, a segment, a subsegment, and an inferred segment.

Maps to: Objective 2 (Comprehension).

A trace holds all the segments that one request generated, and it is identified by a trace ID. A segment records the work of one service for the request. A subsegment records a downstream call or a block of code inside a segment. When a service such as DynamoDB sends no segment, X-Ray builds an inferred segment from the caller’s subsegment, so that the dependency still appears on the service map.

Question 3: Explain how sampling and the tracing header work together, and what the default sampling rule does.

Maps to: Objective 3 (Comprehension).

The first X-Ray-integrated service that a request reaches decides whether to sample it, and adds the X-Amzn-Trace-Id header with the trace ID and the sampling decision. Each service passes the header downstream, so all services agree. By default, X-Ray traces the first request each second and five percent of the additional requests, and you can add rules that match the path, the method, or the service.

Question 4: Show how to turn on tracing for a Lambda function behind API Gateway, with infrastructure as code.

Maps to: Objective 4 (Application).

Set TracingConfig Mode to Active on the AWS::Lambda::Function resource, and attach the AWSXRayDaemonWriteAccess managed policy to its execution role, or allow xray:PutTraceSegments and xray:PutTelemetryRecords. In the AWS Serverless Application Model, use Tracing: Active. Turn on tracing for the API Gateway stage, for example with the TracingEnabled property of the AWS::ApiGateway::Stage resource.

Question 5: Explain how to find all traces for the gold customer tier that took longer than five seconds.

Maps to: Objective 5 (Application).

Record the customer tier as an annotation in the application code, because annotations are indexed. Then use a filter expression that combines the annotation and the response time, for example annotation.tier = "gold" and responsetime > 5. Metadata would not work, because it is not indexed. If you need this view often, save the filter expression as a group.

Question 6: Compare AWS X-Ray, Amazon CloudWatch, AWS CloudTrail, and AWS Config.

Maps to: Objective 6 (Analysis).

CloudWatch collects metrics and logs and runs alarms for resources. CloudTrail records the API calls made in the account, for audit. AWS Config records resource configuration over time and checks it against rules. X-Ray traces requests across services and finds the slow or failing step. A slow checkout across many services points to X-Ray, and a question about who deleted a bucket points to CloudTrail.

Question 7: Design a tracing setup for FlashCart’s checkout, which uses API Gateway, Lambda, ECS, and DynamoDB.

Maps to: Objective 7 (Synthesis).

Turn on tracing for the API Gateway stage, set Lambda to Active with the write permissions, and instrument the ECS service with OpenTelemetry through the AWS Distro for OpenTelemetry, because the SDK and daemon are in maintenance mode. Add a sampling rule that traces every checkout request and samples health checks at a low rate. Create a group for faults with Insights and a CloudWatch alarm, give read access only to the teams that need it, use a KMS key if required, and define all of it in CloudFormation so that every environment is traced the same way.
