1. Version Control With Git

Problem Statement

FlashCart’s CloudFormation templates live on three laptops and on a shared drive in a folder named templates-final-v2. Last week production broke after someone deployed an older copy of a template. Nobody can say who opened a security group rule, or why.

The architects ask for one place where every infrastructure file is stored, with a full history of who changed what and why.

Your challenge:

  • Explain why infrastructure files belong in version control.
  • Describe the main Git concepts and commands.
  • Choose where the Git repository lives.

1.1 Why Version Control for Infrastructure

  • Infrastructure as code is text, so it can be stored, compared, and restored like application code.
  • Version control records every change to a file: what changed, who changed it, when, and why.
  • It gives a team history, review before a change is applied, rollback to a known good version, and collaboration without overwriting each other.
  • It also gives auditors an answer to “who changed the security group, and why?”
  • The same applies to every file type in this lesson: CloudFormation templates, Terraform files, Python scripts, and architecture documents.

1.2 Git Concepts

ConceptWhat it is
Repository (repo)A project folder with its full history stored by Git.
CommitA saved snapshot of the changes, with an author, a time, and a message.
BranchA separate line of commits. You make changes on a branch without touching the main branch.
MergeCombining the commits of one branch into another.
RemoteA copy of the repository on a server, such as GitHub, that the team shares.
Clone, push, pullCopy a remote repository to your computer, send your commits to the remote, and bring the remote’s new commits to your computer.
Pull request (PR)A request to merge a branch, which gives others a place to review and discuss the change first.
TagA named point in history, for example a release.

1.3 Core Git Commands

CommandWhat it does
git init -b mainCreates a new repository whose first branch is named main.
git statusShows which files changed and what is staged.
git add Stages a change so that it goes into the next commit.
git commit -m "message"Saves the staged changes as a commit.
git diffShows the changes that are not staged yet.
git log --onelineLists the commits, one per line.
git switch -c Creates a branch and switches to it.
git merge Merges a branch into the current branch.
git push and git pullSend commits to the remote and bring new commits from it.
git revert Adds a new commit that undoes an earlier commit, and keeps the history.

1.4 Where the Repository Lives

  • A team shares a repository on a Git host. Common hosts are GitHub, GitLab, and Bitbucket.
  • AWS CodeCommit is the managed Git service from AWS, with access controlled by IAM. AWS closed it to new customers in 2024, and then returned it to general availability on November 24, 2025, so new customers can create repositories again. Older books and slides still say that it is closed.
  • Whichever host you choose, the Git workflow in this lesson is the same.

2. Git Workflows and Pull Requests

Problem Statement

Two FlashCart engineers changed the same template on the same day, and the second one overwrote the first. The team lead wants every change reviewed before it reaches production, and a quick way to undo a bad change.

Your challenge:

  • Describe the steps of the GitHub flow.
  • Compare the GitHub flow with trunk-based development and Gitflow.
  • Protect the main branch, and undo a change safely.

2.1 The GitHub Flow

  • The GitHub flow is a lightweight, branch-based workflow. GitHub itself uses it for its site policy, documentation, and roadmap, so it suits documents as well as code.
  • Your branch is a safe place to make changes. Your changes do not reach the default branch until you merge.
StepWhat you do
1. Create a branchUse a short, descriptive name, such as add-s3-log-bucket.
2. Make changes and commitCommit and push to your branch. Give each commit a descriptive message.
3. Create a pull requestSummarize the changes and the problem that they solve. Link the issue if there is one. Mark it as a draft if you want early feedback.
4. Address review commentsReviewers comment on the whole pull request or on single lines. You keep committing to the branch, and the pull request updates.
5. MergeWhen the pull request is approved and the checks pass, merge it into the default branch.
6. DeployA pipeline or a service applies the merged change. See tab 5.
7. Delete the branchThis shows that the work is done and prevents old branches from being used by accident. The history stays.

2.2 Other Branching Models

ModelHow it worksFits
GitHub flowOne main branch that is always deployable. Short-lived feature branches and pull requests.Most teams, and infrastructure and documentation repositories.
Trunk-based developmentEveryone merges small changes to main very often, in short-lived branches or directly. Feature flags hide unfinished work.Teams with strong automated tests and frequent releases.
GitflowLong-lived main and develop branches, plus feature, release, and hotfix branches.Products with scheduled releases and several versions in the field.

2.3 Good Commits and Pull Requests

  • Give each commit a descriptive message, for example “Allow HTTPS from the load balancer security group”.
  • Make each commit one isolated, complete change. If you rename a variable in one commit and add tests in another, you can later revert the rename and keep the tests.
  • Make a separate branch for each set of unrelated changes. It is easier for reviewers to give feedback, and a delay in one change does not hold up the others.
  • Explain the what and why in the pull request. For infrastructure, add what the change does in AWS and what the risk is, for example whether a resource is replaced.

2.4 Protecting the Main Branch

  • A protected branch has rules that every change must follow. On GitHub, you can require pull requests with a number of approving reviews, and require status checks to pass before a merge.
  • You can require a review from the code owner of the files that the pull request changes. For example, the network team owns the network templates.
  • You can require a linear history, which stops merge commits and can make changes easier to reverse.
  • By default, GitHub blocks force pushes to a protected branch and blocks deleting it.
  • When a person pushes new code to an approved pull request, the approval can be dismissed, so the reviewer sees the new change.

2.5 Undoing a Change

  • On a shared branch, use git revert. It adds a new commit that reverses an earlier commit, and the history stays complete. You then deploy the reverted version.
  • Do not rewrite shared history with a force push. Other people’s copies would no longer match.
  • A bad change on your own branch is easy: commit a fix, or delete the branch.

2.6 Practice: A Local Git Workflow

  • You can practice in AWS CloudShell, or in any terminal where Git is installed. You need no GitHub account. Create a small CloudFormation template, and follow the commands below.
git init -b main
mkdir templates
# Create templates/network.yaml in your editor, then:
git add templates/network.yaml
git commit -m "Add network template"

git switch -c add-s3-log-bucket
# Edit templates/network.yaml to add an S3 log bucket, then:
git diff
git add templates/network.yaml
git commit -m "Add S3 log bucket with versioning"

git switch main
git merge --no-ff add-s3-log-bucket
git log --oneline

# Undo the merge by adding a new commit that reverses it:
git revert -m 1 HEAD
  • These commands were written for this course. Check each result with git log --oneline and git status.
  • The option --no-ff makes Git create a merge commit even when it could simply move the branch forward. The last command reverses that merge commit. The -m 1 option tells Git to keep the first parent, which is the main branch.

3. What Belongs in the Repository

Problem Statement

A contractor pushed a Python script to a public repository, and the script contained an AWS access key. Another engineer committed a Terraform state file. The architecture diagram in the company wiki shows a database that was removed months ago.

The team lead asks what belongs in the repository, what must never be in it, and how the documents can stay accurate.

Your challenge:

  • Lay out a repository for infrastructure code, scripts, and documents.
  • Decide which files to commit and which to ignore.
  • Keep secrets out of Git, and know what to do when one gets in.

3.1 A Repository Layout

  • Keep the infrastructure, the scripts, and the documents that describe them in the same repository, so that one pull request can change all of them together.
  • Use one folder for each kind of file, and a README that tells a new person where to start.
flashcart-infra/
  README.md
  .gitignore
  docs/
    architecture.md
    decisions/
      0001-use-cloudformation-for-network.md
  cloudformation/
    network.yaml
    stack-deployment/
      network-dev.yaml
  terraform/
    modules/
    environments/
      dev/
        main.tf
        .terraform.lock.hcl
  scripts/
    requirements.txt
    stack_status.py
  • This layout was written for this course. Many teams use separate repositories for separate teams or services. The idea is the same: a clear place for each kind of file.

3.2 What to Commit, and What Never To

Commit itNever commit it
CloudFormation templates and stack deployment filesAWS access keys, passwords, tokens, and private keys such as .pem files
Terraform files (.tf) and the dependency lock file .terraform.lock.hclTerraform state files (.tfstate), which can hold sensitive values in plain text
Python scripts, tests, and requirements.txtVirtual environments, caches, and compiled files
README files, architecture documents, diagrams as code, and decision recordsVariable files that hold secrets, such as .tfvars, and .env files
An example variable file with no real values, such as example.tfvarsLarge generated files that you can rebuild

3.3 The .gitignore File

  • A .gitignore file lists the files that Git must not track. Commit it, so that everyone ignores the same files.
  • It stops accidents, but it does not remove a file that is already tracked.
  • Do not ignore .terraform.lock.hcl. Terraform recommends that you keep it in version control so that everyone uses the same provider versions.
# Terraform
.terraform/
*.tfstate
*.tfstate.*
crash.log
*.tfvars
!example.tfvars
override.tf
override.tf.json
*_override.tf

# Python
__pycache__/
*.pyc
.venv/

# Secrets and keys
.env
*.pem
*.key

3.4 Keeping Secrets Out of Git

  • Keep secrets in AWS Secrets Manager or AWS Systems Manager Parameter Store, and let the template or the script read them at run time. CloudFormation dynamic references do this for templates (Lesson 296.1).
  • Run code with an IAM role or temporary credentials, and not with a stored access key.
  • Use git-secrets, an open-source tool from AWS Labs, to stop a commit that contains a secret. Run git secrets --register-aws to add the AWS patterns, git secrets --scan to scan the files, and git secrets --scan-history to scan the history.
  • Turn on secret scanning with push protection on your Git host, if it offers it.
  • If a key is committed: deleting the commit is not enough, because other copies and forks can still hold it. Deactivate the access key in IAM at once, create a new one if it is needed, and review what the key did.

3.5 Keeping Documentation Accurate

  • Treat architecture documentation as docs as code: write it in plain text, such as Markdown, keep it in the repository, and change it in the same pull request as the infrastructure.
  • A pull request that changes the infrastructure should show a change in the documents, or say why none is needed. Reviewers can check this.
  • A document in a wiki, without history, drifts away from the real infrastructure. A document in Git is reviewed with every change.

Ignore the state, hide the keys, keep the lock file, and keep the docs next to the code.

4. Working With Infrastructure, Scripts, and Documentation

Problem Statement

FlashCart’s repository will hold CloudFormation templates, Terraform modules, Python scripts, and architecture documents. Each kind of file fails in a different way, so each needs its own checks and its own review questions.

Your challenge:

  • Check CloudFormation files and deploy them from Git.
  • Handle Terraform files and state safely in a team.
  • Write Python scripts that are safe to keep in Git, and keep architecture documents accurate.

4.1 CloudFormation Files

  • Run cfn-lint to check a template against the CloudFormation specification and best practices. AWS describes using it as a Git pre-commit hook, as an editor plugin, and as a step in a build pipeline. Install it with pip install cfn-lint, and run cfn-lint template.yaml.
  • Run aws cloudformation validate-template to check the template structure and syntax. It does not prove that the stack will be created.
  • Preview the effect with a change set (Lesson 296.1) before you merge, so that the reviewer sees what is added, changed, or replaced.
  • Keep the stack deployment file with the template. It holds the parameters for one environment.
  • CloudFormation Git sync monitors a repository for changes to the template file and the deployment file, and updates the stack when you commit a change (tab 5).
template-file-path: cloudformation/network.yaml
parameters:
  Environment: dev
tags:
  Project: FlashCart
  • This deployment file follows the structure in the CloudFormation Git sync documentation: the path of the template, the parameters, and the tags. The values are examples.

4.2 Terraform Files

  • Commit the .tf files and the .terraform.lock.hcl dependency lock file. Do not commit the .terraform folder, the state files, or variable files that hold secrets.
  • State records which real resources Terraform manages. It can hold sensitive values in plain text, and Git cannot lock it, so two people could apply at the same time and corrupt it.
  • Store state in a remote backend, such as an S3 bucket with encryption and versioning. With use_lockfile = true, the S3 backend locks the state while one person applies. Native S3 locking needs Terraform 1.10 or later.
  • Run terraform fmt -check and terraform validate on every pull request, and run terraform plan so that the reviewer sees the planned changes.
  • Apply from the main branch after the merge, and not from a laptop.
terraform {
  backend "s3" {
    bucket       = "flashcart-terraform-state"
    key          = "dev/network/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true
  }
}
  • This sample was written for this course. The bucket name and key are examples.

4.3 Python Scripts

  • Commit the script, its tests, and requirements.txt, so that everyone installs the same libraries. Keep the virtual environment out of Git.
  • Do not put an access key, a password, or an account-specific value in the script. Use the default credential chain of the AWS SDK for Python (boto3), which finds a role, a profile, or temporary credentials. Read other settings from environment variables or from Parameter Store.
  • Give the script the least privilege that it needs, and document which IAM permissions it requires.
  • In a pull request, check what the script changes in AWS, and whether it is safe to run twice.
import boto3


def stack_status(stack_name):
    # No keys in the code. boto3 uses the default credential chain,
    # for example a role, a profile, or temporary credentials.
    cfn = boto3.client("cloudformation")
    return cfn.describe_stacks(StackName=stack_name)["Stacks"][0]["StackStatus"]


if __name__ == "__main__":
    print(stack_status("flashcart-dev"))
  • This script was written for this course. It has no keys in it.

4.4 Architecture Documentation

  • Write the documents in plain text. A README explains the purpose and how to use the repository. A docs folder holds the architecture description.
  • Record important choices as architectural decision records (ADRs). An ADR captures the decision, the context, and the considerations. AWS Prescriptive Guidance describes the ADR process, and it names three anti-patterns: no decision is made, a decision has no justification, and a decision is not recorded.
  • Draw diagrams as code, so that a change to a diagram is a readable change in a pull request. GitHub renders Mermaid diagrams that you write in a Markdown file.
  • When a picture exported from a drawing tool is better, commit the image and the source file together, and write alt text.
# 0001. Use CloudFormation for the network layer

Status: Accepted
Date: 2026-10-30

## Context
The team needs a repeatable network for dev, test, and prod, and the team already uses CloudFormation.

## Decision
Define the VPC, subnets, and route tables in CloudFormation templates in this repository.

## Consequences
Network changes go through pull requests. Terraform is not used for the network layer.

```mermaid
flowchart LR
  User --> ALB[Application Load Balancer]
  ALB --> ECS[ECS service]
  ECS --> RDS[(RDS database)]
```
  • Both samples were written for this course.

File typeAutomated checkReviewer question

5. Automating Checks and Deployments

Problem Statement

Reviewers at FlashCart keep finding the same mistakes by eye: an open port, a missing tag, an unformatted file. Management wants these checks to run automatically before a pull request can merge.

Management also wants deployments to run from the main branch, without AWS access keys stored in the pipeline.

Your challenge:

  • Run checks on the developer’s computer and on every pull request.
  • Deploy from Git, including with CloudFormation Git sync.
  • Give a pipeline AWS access without long-lived keys, and roll back a bad change.

5.1 The Checked Path From Change to Deployment

5.2 Checks on the Developer’s Computer

  • A Git hook is a script that Git runs at a point in the workflow. A pre-commit hook runs before a commit is created, and it stops the commit if the script fails.
  • A pre-commit hook catches simple problems early, before a reviewer sees them.
  • Hooks run only on the computer where they are installed, so they help but do not enforce. Repeat the same checks in the pull request.
#!/bin/sh
# Save as .git/hooks/pre-commit and make it executable.
cfn-lint cloudformation/*.yaml || exit 1
terraform fmt -check -recursive terraform || exit 1
git secrets --scan || exit 1
  • This hook was written for this course. It needs cfn-lint, Terraform, and git-secrets to be installed.

5.3 Checks on Every Pull Request

  • A continuous integration (CI) workflow runs on each pull request, and its result appears as a status check. With branch protection, the merge is blocked until the required checks pass.
  • The checks are the same as in section 4.5: lint, validate, plan or change set, tests, and a secret scan.
CheckCatches
cfn-lint and validate-templateSyntax errors, wrong properties, and unused parameters in CloudFormation.

5.4 AWS Access Without Long-Lived Keys

  • Do not store an AWS access key as a secret in the Git host. A stored key is long-lived, and it can leak.
  • With OpenID Connect (OIDC), a GitHub Actions workflow gets a short-lived token for each run, and exchanges it for temporary AWS credentials by assuming an IAM role.
  • You add GitHub’s OIDC provider, https://token.actions.githubusercontent.com, to IAM, and you create a role that trusts it. The job needs the permission id-token: write to request the token. That permission does not let the workflow change any resource.
  • In the role’s trust policy, use the token.actions.githubusercontent.com:sub condition key, so that only your repository and branch can assume the role.
  • Give the role least privilege. Use a read-only role for pull request checks, and a separate role for deployments from main.

5.6 Rolling Back

  • To undo a bad change, revert the commit in Git, open a pull request for the revert, and let the same pipeline deploy the earlier state.
  • CloudFormation also rolls back by itself when a stack operation fails (Lesson 296.1).
  • For Terraform, keep versioning on the state bucket, so that an earlier state can be recovered.
  • A rollback does not bring back deleted data, so protect data stores with DeletionPolicy, snapshots, and backups.

6.4 Lesson Summary

  • Version control gives infrastructure history, review, rollback, and collaboration. The same Git workflow applies to CloudFormation files, Terraform files, Python scripts, and architecture documents.
  • The GitHub flow uses a short-lived branch, small commits, a pull request, review and checks, a merge, a deployment, and branch deletion. Protect main with required reviews and status checks, and undo a change with git revert.
  • Commit the code, the lock file, and the documents. Never commit keys, passwords, state, or secret variable files. Use .gitignore, git-secrets, and secret scanning, and deactivate a leaked key in IAM.
  • Check CloudFormation files with cfn-lint, validate-template, and a change set. Check Terraform files with fmt, validate, and plan, and keep state in a locked S3 backend. Write Python scripts without keys, and keep documents as code.
  • Run checks locally and on every pull request. Deploy from main with CloudFormation Git sync or a pipeline, and give the pipeline access with OIDC and an IAM role, not stored keys.

Memory Hook

Branch, review, merge, deploy. Ignore the state, hide the keys, and keep the docs next to the code.

7. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: Explain why infrastructure files belong in version control.

Maps to: Objective 1 (Knowledge).

Infrastructure files are text, so Git can record every change with its author, time, and reason. That gives the team history, review before a change is applied, rollback to a known good version, and collaboration without overwriting each other. It also gives auditors an answer to who changed a resource and why.

Question 2: Describe the steps of the GitHub flow, and how it differs from Gitflow.

Maps to: Objective 2 (Comprehension).

In the GitHub flow, you create a branch, commit small changes, open a pull request, address review comments while the checks run, merge into main, deploy from main, and delete the branch. Main is always deployable. Gitflow keeps long-lived main and develop branches plus feature, release, and hotfix branches, which suits products with scheduled releases.

Question 3: Show how to protect the main branch and how to undo a bad change.

Maps to: Objective 3 (Application).

Add branch protection rules that require pull requests with approving reviews, required status checks, and optionally code owner reviews and a linear history. Force pushes and deleting the branch stay blocked. To undo a bad change on a shared branch, use git revert to add a commit that reverses it, open a pull request, and deploy the reverted version. Do not rewrite shared history.

Question 4: List what to commit and what never to commit in an infrastructure repository, and explain what to do about a leaked key.

Maps to: Objective 4 (Application).

Commit templates, deployment files, .tf files, .terraform.lock.hcl, Python scripts, tests, requirements.txt, and documents. Never commit access keys, passwords, private keys, Terraform state, or variable files with secrets, and use .gitignore, git-secrets, and secret scanning. If a key is committed, deactivate it in IAM at once, because deleting the commit does not remove other copies. Create a new key only if it is needed, and review what the key did.

Question 5: Compare the checks for CloudFormation files, Terraform files, Python scripts, and documents.

Maps to: Objective 5 (Analysis).

CloudFormation: cfn-lint, validate-template, and a change set that shows replaced or deleted resources. Terraform: fmt, validate, and plan, with the state in a remote locked backend. Python: a linter, tests, a secret scan, and a check that the script uses a role and not keys. Documents: a review against the change, links that work, and an ADR for a major decision.

Question 6: Explain how a pull request check can use AWS without a stored access key, and how CloudFormation Git sync deploys from Git.

Maps to: Objective 6 (Analysis).

With OIDC, the workflow requests a short-lived token for each run, and exchanges it for temporary AWS credentials by assuming an IAM role. The IAM trust policy limits the role to a repository and branch with the sub condition key, and the job needs the id-token: write permission. CloudFormation Git sync links a repository through CodeConnections, monitors the template file and the stack deployment file on one branch, and updates the stack when you commit a change. It can also comment on a pull request with the planned changes.

Question 7: Design a repository and a workflow for FlashCart’s CloudFormation, Terraform, Python, and architecture documents.

Maps to: Objective 7 (Synthesis).

Use one repository with folders for CloudFormation, Terraform, scripts, and docs, a README, and a .gitignore that excludes state, keys, and variable files. Use the GitHub flow with a protected main branch, required reviews, code owners for each area, and required checks: cfn-lint, validate-template, terraform fmt, validate, and plan, a Python linter and tests, and a secret scan. Run the checks locally with a hook and on every pull request through OIDC roles. Deploy from main with CloudFormation Git sync for stacks and a pipeline for Terraform with S3 state and locking, and revert the commit to roll back. Keep ADRs and diagrams as code in the same pull request as the change.
